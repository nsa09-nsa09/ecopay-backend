# FreedomPay contract audit (backend)

Sources checked 2026-10: docs.freedompay.kz (Apidog; raw pages via `/llms.txt`), the legacy
merchant-api docs still published on freedompay.kz (`/docs-en/merchant-api/*`, RU `/docs/*`) and
the official PayBox SDKs on GitHub (PayboxCore / PayboxPay / PayboxPayout / PayboxCardStorage).
"UNVERIFIED" items must be confirmed with the FreedomPay manager or in the sandbox (section J of
the release report).

| Area | Code before | Current FreedomPay doc | Action |
|---|---|---|---|
| Purchase init | `/init_payment.php`, no `pg_auto_clearing`, no `pg_lifetime` | `init_payment.php`; `pg_auto_clearing` default **0 = two-step** (hold, auto-cleared ≤5 days); `pg_lifetime` seconds | Send `pg_auto_clearing=1` (one-step; configurable, prod guard rejects two-step) and `pg_lifetime=1800` aligned to the 30-min seat reservation. Success requires signed `ok` **and** a redirect URL. |
| One- vs two-step | Not modelled; any "ok" status = captured | `pg_captured` 0/1 in status & result callback; `/do_capture.php`, `/cancel` | `ProviderPaymentState` (PENDING/AUTHORIZED/CAPTURED/FAILED/EXPIRED/PARTIALLY_REFUNDED/REFUNDED/UNKNOWN). AUTHORIZED never activates a member or creates a payout: intent → RECONCILING + review. |
| Owner payout hold | `hold-days` comments mixed "held in merchant balance" with capture | n/a (EcoPay-internal) | Kept the 30-day **owner payout reserve** (`releaseAt = capturedAt + app.payout.hold-days`, prod guard = 30). Terminology: authorization/capture = provider card state; payout hold/reserve = EcoPay settlement state. |
| Status | `/get_status.php`, reads `pg_transaction_status`, "ok" = success | `/get_status3.php`: `pg_payment_status`, `pg_captured`, `pg_clearing_amount`, `pg_refund_amount`/`pg_revoke_amount`, `pg_refund_payments[]`; lookup by `pg_payment_id` **or** `pg_order_id` | Adapter on get_status3 with explicit state model, amount/currency extraction, refunded totals (incl. nested lists), not-found (11068/340) handling, lookup by order id for ambiguous initiations. Enum values: current docs only show `success`; legacy `ok/pending/partial/new/failed/incomplete/revoked` all mapped — **UNVERIFIED** full current enum. |
| Result callback | Signed with script = controller literal; dedup key included `pg_salt` (each retry = new inbox row) | Script = last segment of our result URL; retried every 30 min for 2 h; `pg_captured`, `pg_card_token`, `pg_recurring_profile_id` | Signature checked at accept and again before applying money; dedup key = digest of content **without** salt/sig (identical retries collapse); invalid-signature rows keyed by full raw content (cannot poison a genuine key). Amount/currency mismatch → CAPTURE_ANOMALY. `pg_captured=0` → not captured. |
| Browser return | `confirm-success` held the intent row lock during the HTTP status call; no amount check | Success URL is not proof of payment | Return endpoint now: read → provider call without locks → apply under lock with re-check; amount/currency verified; browser params ignored. Plus a scheduled reconciliation (2-min cadence, 20/batch, 1.5 s spacing, attempt cap) for lost callbacks. |
| Recurring | `/recurring.php` (does not exist in any source); sync `ok` = captured; all ACTIVE members loaded at once; `@Transactional` bypassed by self-invocation | `/make_recurring_payment` (`pg_recurring_profile`, `pg_result_url`); docs do not state sync `ok` = captured | Current endpoint; sync `ok` = accepted only (intent stays PENDING until callback/status); timeout → UNKNOWN, reconciled, never retried blindly; keyset batches of 200; real transactions; cluster lock. **Production still refuses `app.recurring.enabled=true`** — auto-renewal is not in the MVP launch and the contract is partly UNVERIFIED. |
| `pg_recurring_lifetime` | `recurringLifetimeDays=156` | Unit is **months** (legacy "min 1 (1 month), max 156"); current docs max **12** | Renamed to `recurring-lifetime-months` (env `FREEDOMPAY_RECURRING_LIFETIME_MONTHS`, default 12), clamped 1..12. |
| Refund / cancel | `/revoke.php` always; network error → retried (could refund twice); no reconciliation of PENDING_PROVIDER (no refund id is returned) | `/revoke` (captured, partial allowed); `/cancel` (uncaptured two-step, full only); response has no refund id | Reads provider state first: AUTHORIZED → `/cancel` (full only), CAPTURED → `/revoke`; state read failure = not sent (safe retry). Ambiguous submission → PENDING_PROVIDER, never resent. PENDING_PROVIDER settled from get_status3 refunded totals; not visible after 24 h → REQUIRES_REVIEW. `legacy-php-endpoints` toggle keeps `.php` paths available. |
| Payout card tokenization | `cardstorage/add2` (purchase card storage, merchant secret); fallback took the **newest card from `cardstorage/list`** (could attach an unrelated purchase card); purchase saved cards could be registered as payout destinations (`POST /payouts/methods`) | `/v1/merchant/{id}/cardstoragepayout/add` — cards "can only be used for payouts"; no order id; callback = post_link | Binding now uses `cardstoragepayout/add`; matched by returned `pg_payment_id`, callback `pg_user_id` must equal the binding owner; method created **only** from that signed callback (`token_source=PAYOUT_CARD_TOKEN`); return page never connects a card; no list fallback; `POST /payouts/methods` returns `PAYOUT_CARD_BINDING_REQUIRED`. Existing methods → `REQUIRES_REBIND` (V88), never dispatched to; payouts wait in PENDING_METHOD. Sandbox-verified (2026-10-06): script `add` signed with the **merchant** secret; the payout secret and `add2` are rejected with error 1100 (HTTP 401) → default `payout-card-storage-uses-payout-secret=false`. Callback field list **UNVERIFIED** (assumed same as cardstorage post_link). |
| reg2reg payout | Exception → retry → REQUIRES_REVIEW; batch exception → immediate review; reconciliation required provider id | `/api/reg2reg` (payout secret, `pg_card_token_to`, `pg_order_id`, status ok/error/process) | Ambiguous submission → PENDING_PROVIDER and reconciliation by **order id** (payment_status2 accepts it); never resent; not-found after 30 min → REQUIRES_REVIEW. Fixed a query bug that would have left such payouts PENDING_PROVIDER forever. |
| Payout status | `payment_status2` with payment id + order id | `pg_order_id` required, `pg_payment_id` optional; `payment_id=0` = does not exist | Order-id-only lookups; `payment_id=0`/11068 → not found; amount compared before settlement. |
| Payout callback | Matched by provider id only; amount ignored | `pg_payment_id`, `pg_order_id`, `pg_status`, `pg_payment_amount` | Matched by provider id or order id; amount mismatch → REQUIRES_REVIEW; verified with the payout secret (purchase-secret signatures rejected); duplicate callbacks are no-ops. |
| Card list/delete | `cardstorage/list` used for payout binding | Same `cardstorage/list|remove` for both families; no `cardstoragepayout/list` documented | No longer used in money paths. Whether list covers payout-only cards is **UNVERIFIED**. |
| Response signatures | Never verified | "Requests AND responses are signed"; only merchant-not-identified (9998 / legacy 101) is unsigned | Every response verified with the request's script + secret (constant-time). Invalid/missing signature → `FreedomPaySignatureException` → UNKNOWN/RECONCILING, never success, never member activation, payout/refund success or payout-method creation. Unsigned answers accepted only as `pg_status=error`. Metric `ecopay_freedompay_response_invalid_signature_total`. |
| Signature algorithm | `TreeMap` (duplicates collapsed), platform charset, nested XML ignored | values sorted by name, same-name fields keep message order, recursive for nested XML, all extra fields included, MD5 lowercase | `FreedomPayMessage` keeps repeated + nested fields; explicit UTF-8; tests with doc-derived fixtures. Webhooks accepted as multi-value maps; `pg_xml` callbacks unwrapped. Nested form-encoded arrays (`pg_receipt_positions[]`) are not sent by EcoPay; flattening rule **UNVERIFIED**. |
| XML / client | No size limit; `RestClient` defaults; unlimited concurrency; errors logged with messages | — | XXE + secure processing kept; 256 KB body cap and depth limit before parsing; connect 5 s / read 20 s; bulkhead 16 in-flight per instance (not-sent on saturation); read-only calls retried ≤2 with jitter, money calls never; sanitized logs; latency/outcome timer `ecopay_freedompay_request`. |
| Rate guidance | — | 1.5–2 s between payment API calls recommended | Reconciliation spaced 1.5 s, bounded batches. |

## Sandbox verification (2026-10-06)

`FreedomPaySandboxContractTest` (opt-in: `FREEDOMPAY_SANDBOX_IT=1` + `FREEDOMPAY_SANDBOX_*` env vars,
refuses any non-`test-api.` host) ran the production adapter against `test-api.freedompay.kz`.
Only money-free calls: an unpaid payment page, status reads, an uncompleted payout-card session.

| Call | Result |
|---|---|
| `init_payment.php` (one-step, `pg_lifetime`, idempotency key) | `ok`, response signature **verified**, redirect URL + payment id returned |
| `get_status3.php` by payment id and by order id | signature verified; unpaid page = `new` → PENDING; amount 100.00 / KZT parsed; order lookup returns the same payment id |
| `get_status3.php` unknown order | error 11068 → `notFound` |
| `api/payment_status2` unknown order | error 11068 → `notFound` (never success) |
| `cardstoragepayout/add`, script `add`, merchant secret | `ok`, signed, `pg_payment_id` + `pg_redirect_url` (what the gateway reads) |
| same with payout secret, or script `add2` | HTTP 401, unsigned `error` 1100 "invalid request signature" |
| `cardstoragepayout/add2` | HTTP 404 (endpoint does not exist) |

Still not exercised (needs a card entered on the hosted page or real funds flow): result /
payout-card callbacks, captured status, `/revoke`, `/cancel`, `reg2reg`, `make_recurring_payment`.
